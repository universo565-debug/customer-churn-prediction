## Project Description

A telecom company loses revenue every time a customer cancels their service.
Because acquiring a replacement customer costs several times more than retaining
an existing one, even a modest reduction in churn has an outsized effect on
profitability.

This project answers two questions:

1. **Which customers are about to leave?** — so the retention team can target a
   limited budget at the people who actually need intervention.
2. **What is driving them out?** — so leadership can fix the products and
   contract structures that manufacture churn in the first place.

The deliverable is a regularized logistic regression classifier wrapped in a
leak-free scikit-learn pipeline, tuned by cross-validation, evaluated on a
held-out test set, interpreted through odds ratios, and serialised for
deployment.

### Dataset

[Telco Customer Churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn)
— 7,043 customers × 21 features.

| Group | Features |
|---|---|
| **Demographics** | `gender`, `SeniorCitizen`, `Partner`, `Dependents` |
| **Services** | `PhoneService`, `MultipleLines`, `InternetService`, `OnlineSecurity`, `OnlineBackup`, `DeviceProtection`, `TechSupport`, `StreamingTV`, `StreamingMovies` |
| **Account** | `tenure`, `Contract`, `PaperlessBilling`, `PaymentMethod`, `MonthlyCharges`, `TotalCharges` |
| **Target** | `Churn` (Yes / No) |

## Usage Example

Once the notebook has been run and `customer_churn_model.pkl` exists, the saved
pipeline can be loaded and used on new customer records:

```python
import joblib
import pandas as pd

model = joblib.load('customer_churn_model.pkl')

new_customer = pd.DataFrame({
    'gender': ['Male'],
    'SeniorCitizen': [0],
    'Partner': ['No'],
    'Dependents': ['No'],
    'tenure': [1],
    'PhoneService': ['Yes'],
    'MultipleLines': ['No'],
    'InternetService': ['Fiber optic'],
    'OnlineSecurity': ['No'],
    'OnlineBackup': ['No'],
    'DeviceProtection': ['No'],
    'TechSupport': ['No'],
    'StreamingTV': ['No'],
    'StreamingMovies': ['No'],
    'Contract': ['Month-to-month'],
    'PaperlessBilling': ['Yes'],
    'PaymentMethod': ['Electronic check'],
    'MonthlyCharges': [75.75],
    'TotalCharges': [75.75],
    'TotalServices': [2],     # engineered feature
})

probability = model.predict_proba(new_customer)[:, 1][0]
print(f"Churn probability: {probability:.2%}")
```

The notebook defines a `predict_churn()` helper that is easier to use than the
raw pipeline — it accepts a plain dict, **derives `TotalServices` for you**,
validates the input columns, supports batch scoring, and returns a tidy
DataFrame with a probability and a Low/Medium/High risk band:

```python
results = predict_churn(new_customer_dict)
#   churn_prediction  churn_probability  risk_level
#   Yes               0.7xxx             High
```

The threshold is exposed as an argument (`predict_churn(data, threshold=0.35)`)
so the flag volume can be matched to the retention team's actual capacity.

## Methodology

| Phase | What happens |
|---|---|
| **1. Setup** | Install `kagglehub`, import libraries |
| **2. Exploration** | Shape/dtypes/statistics, missing-value forensics, target distribution, 6 visualizations |
| **3. Preprocessing** | Drop `customerID`, engineer `TotalServices`, `ColumnTransformer` with `StandardScaler` + `OneHotEncoder` |
| **4. Modeling** | Stratified 80/20 split, `GridSearchCV` over `C` (5-fold, scored on ROC-AUC) |
| **5. Evaluation** | Accuracy / precision / recall / F1 / AUC, confusion matrix, ROC curve, threshold sweep, coefficient interpretation |
| **6. Deployment** | `joblib` serialisation, `predict_churn()` function, 3 worked examples + batch scoring |
| **7. Summary** | Auto-generated findings block |

### Design decisions worth flagging

- **Everything lives inside one `Pipeline`.** The scaler and encoder are fit on
  training folds only, never on the full dataset. This prevents data leakage
  during both tuning and evaluation, and it means the saved `.pkl` carries its
  own preprocessing so production can never drift out of sync with training.
- **`GridSearchCV` is scored on ROC-AUC, not accuracy.** With a 73/27 class
  imbalance, accuracy rewards a model for nailing the easy majority class. AUC
  measures how well the model *ranks* churners, which is what a retention team
  actually consumes.
- **`stratify=y` on the split**, so both sets preserve the original class ratio.
- **Feature engineering: `TotalServices` (0–9).** The nine service columns encode
  "not subscribed" three different ways (`'No'`, `'No internet service'`,
  `'No phone service'`); the count treats all three as negative. The feature
  proxies *switching cost* — a customer with six services faces far more friction
  leaving than one with a single line.

## Key Findings Summary

### Data quality

- `isnull()` initially reports **zero** missing values — which is wrong.
  `TotalCharges` is stored as `object` and hides **11 blank strings**.
- All 11 affected rows have **`tenure = 0`**: brand-new customers who have not
  been billed a full cycle yet. The missingness is *structural*, not random.
- Dropping them costs 0.16% of the data, leaving **7,032 customers**.
- **Lesson:** always check dtypes against what a column *should* be. A numeric
  column stored as text is a reliable red flag for hidden nulls.

### Exploratory findings

| Finding | Detail |
|---|---|
| **Class imbalance** | ~73% retained / ~27% churned — a "predict nobody churns" model scores ~73% accuracy while being useless |
| **Contract type** | Month-to-month customers churn dramatically more than one- or two-year contract holders. Strongest signal in the dataset |
| **Internet service** | Fiber optic subscribers churn more than DSL; no-internet customers churn least |
| **Tenure** | Churn is front-loaded — risk is highest in the first months and decays sharply |
| **Monthly charges** | Higher bills correlate with higher churn, concentrated in the ~$70–105 range |
| **Multicollinearity** | `tenure` and `TotalCharges` correlate ~0.83 (mechanically, since `TotalCharges ≈ tenure × MonthlyCharges`) — one reason L2 regularization is tuned rather than left at default |

**How to read these for this business problem:**

- **Precision** — of the customers we flagged, how many genuinely churn. Low
  precision means **wasted retention budget**.
- **Recall** — of the customers who churn, how many we caught. Low recall means
  **missed saves**. Since losing a customer costs far more than a wasted
  discount, recall is the more expensive metric to get wrong here.
- **ROC-AUC** — probability the model scores a random churner above a random
  non-churner. Threshold-independent measure of ranking quality.

Recall on the churn class is typically the weakest metric at the default 0.5
threshold, because that cutoff is conservative about predicting a minority
class. Section 5.4 of the notebook sweeps the threshold and shows the
precision/recall/flag-volume trade-off explicitly.

### Churn drivers (consistent across runs)

Logistic regression coefficients are in **log-odds**; exponentiating gives an
**odds ratio**, where >1 increases churn odds and <1 is protective.

| Driver | Direction |
|---|---|
| Two-year / one-year contract | **Strongly protective** — largest effects in the model |
| Longer tenure | Protective |
| Fiber optic internet | Increases risk, even after controlling for price |
| Electronic check payment | Increases risk — manual payment lacks autopay's inertia |
| Tech support / online security | Protective |

**Two caveats stated honestly:** coefficients describe each feature's *marginal*
contribution after the others are held constant, so they can disagree in sign
with the simple bivariate plots — that is the model working, not a bug. And
these are **associations, not proven causes**. The model says month-to-month
customers churn more; it does not prove that moving someone onto a two-year
contract will retain them, since customers who sign long contracts may simply be
more committed to begin with. Confirming causation requires an A/B test.

### Business recommendations

1. **Convert month-to-month customers onto annual contracts** — the largest
   single lever available.
2. **Migrate electronic-check payers to automatic payment** — cheap to execute
   and an independent risk factor in the model.
3. **Concentrate onboarding investment in the first 12 months**, where the
   tenure curve shows risk is steepest.
4. **Investigate fiber optic service quality**, since elevated risk persists
   after controlling for price — pointing at service or competition, not just
   the bill.
5. **Bundle protective add-ons** (tech support, online security), which both
   reduce churn odds and raise switching costs.

## Deployment Considerations

**Batch scoring is the right pattern here.** A weekly job scores the active
customer table and writes probabilities back to the CRM, where retention staff
see a pre-sorted risk list. Churn is slow-moving, so real-time inference buys
nothing; batch is simpler, cheaper, and easier to monitor. A FastAPI/Flask
`/predict` endpoint would only be warranted for live call-centre use.

Production would additionally need: schema and range validation on inputs; model
versioning tied to training date and dataset snapshot; drift monitoring on both
input features and output probabilities; a ground-truth feedback loop (churn is
only observable months later, so log every prediction and join to outcomes);
scheduled quarterly retraining gated on beating the incumbent; and the decision
threshold exposed as a business configuration rather than a hardcoded `0.5`.

**Ethical note.** The dataset includes `gender` and `SeniorCitizen`. Using
protected or sensitive attributes to decide who receives a retention discount
raises fairness and, depending on jurisdiction, regulatory concerns. Before
deployment, audit whether these features contribute materially and consider
removing them — the model's real predictive power comes from contract, tenure,
service, and payment behaviour, all legitimate business variables. Also check
whether error rates differ across demographic groups.
